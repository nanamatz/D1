# Play the Wor!d — Project Instructions

Balatro-inspired word-building roguelite for the web. **The full design document is `docs/GDD.md` — it is the single source of truth.** Every system referenced below cites its GDD section. Art direction is **pixel-art + CRT** (see `docs/UI_DESIGN.md`; the earlier ceramic/un-Balatro guardrail is retired).

## Architecture principles (non-negotiable)

1. **Headless engine.** All game logic lives in `src/engine/` and must never import DOM, React, or browser APIs. The engine must run in Node so `src/sim/` can autoplay thousands of runs for balance verification. UI (`src/ui/`) imports the engine, never the reverse.
2. **Jokers are data + hooks.** Every implemented joker (GDD §11) is a `JokerDef` object registering handlers on the event bus in `src/engine/events.ts`. Never hard-code a joker's effect inside pipeline code. If the pipeline lacks an event a joker needs, add the event. The public roster is Common 34 / Uncommon 57 / Rare 54 / Legendary 5 (150 total); the developer-only Primordial tile is registered separately and never enters production offers or Collection. Synesthete and the superseded Word-Hand-condition tiles are retired, and the separate 97-tile redesign remains postponed.
3. **No magic numbers.** Every tunable value lives in `src/engine/balance.ts`, keyed to GDD tables. New numbers go there first.
4. **Seeded RNG.** All randomness (bag shuffle, shop stock, packs, boss draw) flows through the implemented seeded RNG in `src/engine/rng.ts`. A run is fully reproducible from `RunState.seed`. Never call `Math.random()` in the engine.
5. **TypeScript strict mode.** The types in `src/engine/types.ts` encode GDD decisions (e.g. gibberish = `suit: null, posUsed: null`); keep them authoritative.
6. **Keep docs internally consistent.** When a patch changes a number or a mechanic, grep the docs for stale cross-references and update them in the same pass (e.g. changing the tile total means fixing every "N tiles" mention, not just §2.1; changing the settle/clear flow means updating the pipeline summary, not just the trigger section). Doc drift has caused real contradictions here more than once — a value or rule must read the same everywhere it appears.

## Codex subagent workflow

For non-trivial gameplay, balance, implementation, or bug-fix work, the primary Codex agent is the **Project Manager**. It owns scope, sequencing, decisions, user communication, and the final integrated result. This workflow applies equally in the Codex VS Code extension and the interactive CLI. Use Codex's native subagent tools and the project-scoped custom agents in `.codex/agents/`; **never simulate subagents by launching nested `codex exec` processes or background shell jobs.** `codex exec` is reserved for an explicitly requested non-interactive/CI entry point, not for orchestration inside an active session. Trivial documentation edits, factual questions, and isolated mechanical changes may stay single-agent.

### Delegation rules

- **Delegate explicitly.** For qualifying work, the Project Manager must spawn the named agents below; a plan that merely describes roles without creating the corresponding agent threads is incomplete.
- **Parallelize only independent read-heavy work.** Design analysis, acceptance-test design, repository exploration, log inspection, and review preparation may overlap. Implementation, test-file edits, documentation edits, generated-asset updates, and remediation are write phases and must be sequenced unless the Project Manager assigns disjoint file ownership in advance.
- **One owner per file.** Before any parallel write, record an exclusive file/directory ownership map in the task plan. No agent may edit outside its assigned paths. Shared registries, barrel files, balance tables, lockfiles, generated outputs, and canonical docs always have one writer. If ownership would overlap, serialize the work.
- **Respect dependency order.** An agent must not begin work that depends on an unfinished agent result. Spawn independent work together, wait for all required results, reconcile them, and only then start the dependent phase.
- **Reuse threads.** Send follow-up work to the existing role thread (`game_designer`, `gameplay_programmer`, `qa`, or `code_reviewer`) so it retains its evidence and decisions. Do not spawn duplicate agents for the same unresolved responsibility.
- **Keep the parent authoritative.** Subagents investigate, implement, test, or review only their assigned scope. They must not expand requirements, make product decisions, message the user, create commits/branches, install dependencies, or rewrite unrelated user changes unless the Project Manager explicitly authorizes it.
- **Preserve the working tree.** Every agent checks the existing diff before editing, treats pre-existing changes as user-owned, and never resets, reverts, deletes, or reformats unrelated work. Subagents share the same workspace unless an explicitly prepared worktree is assigned.
- **Propagate constraints.** Every spawn/follow-up message includes the relevant approved spec, acceptance criteria, owned paths, forbidden paths, validation command, and required return format. Never assume a subagent has inferred an unstated decision.
- **Handle blockers honestly.** If an agent hits a spec conflict, missing authority, approval requirement, failing prerequisite, or overlapping edit, it stops that part and returns the evidence to the Project Manager. It must not guess, bypass permissions, or silently reduce scope.

### Required execution sequence

1. **Classify and frame.** The Project Manager decides whether the task is trivial or requires this workflow. For qualifying work, inspect the current working tree, identify the relevant GDD/design sections and source paths, apply the spec-conflict protocol, define one bounded delivery slice, and publish a phase plan before spawning agents.
2. **Plan in parallel.** Spawn `game_designer` for the design/balance brief and `qa` for the initial acceptance matrix in the same phase. Give both the identical scope, constraints, and source-of-truth references. Both remain read-only. Wait for both results.
3. **Resolve the design gate.** Reconcile the two reports against the canonical docs. If behavior is ambiguous, uncovered, or contradictory, stop and ask the user under the spec-conflict protocol. Implementation may begin only after there is one approved brief containing rules, invariants, edge cases, out-of-scope items, and measurable acceptance criteria.
4. **Map the code path.** Send the approved brief to `gameplay_programmer`. For every non-trivial implementation, it first delegates read-only code-path discovery to the built-in `explorer`, waits for the map, and returns or records the affected files, call path, state/data migrations, risk points, and targeted validation plan before editing.
5. **Assign write ownership.** The Project Manager reviews the map and selects one of two modes: (a) one `gameplay_programmer` owns all production edits, or (b) multiple workers receive strictly disjoint paths with one designated integrator for shared files. Default to (a). Record the ownership map before writes begin.
6. **Implement the smallest vertical slice.** `gameplay_programmer` edits only the approved scope, updates affected docs in the same change, adds or updates targeted tests when those tests are inseparable from implementation, and runs the narrowest relevant checks. It returns changed files, behavior implemented, commands run, exact results, and any remaining risk. It does not claim completion from code inspection alone.
7. **Validate independently.** After production writes stop, send the implementation report and diff to the existing `qa` thread. QA reproduces every acceptance criterion, runs focused regression tests plus the required broader suite, and may add minimal test-only coverage while owning those test files. QA never fixes production code. It returns pass/fail per criterion, commands and results, reproduction steps for failures, and coverage gaps.
8. **Review independently.** After QA finishes, spawn or resume `code_reviewer` with the approved brief, code-path map, final diff, and QA report. It remains read-only and reviews correctness, architecture boundaries, state/RNG determinism, documentation consistency, regression risk, GC/allocation behavior, and performance. Findings are ranked `BLOCKER`, `HIGH`, `MEDIUM`, or `LOW` and cite exact files/symbols; no findings must be stated explicitly.
9. **Close the loop.** Route production findings to `gameplay_programmer`, test gaps to `qa`, and design ambiguity to `game_designer`. During remediation, restore exclusive file ownership, run the affected validation again, and have `code_reviewer` re-check all blocking/high findings. Repeat until no blocking/high finding remains or the Project Manager reports a genuine blocker to the user.
10. **Integrate and report.** The Project Manager inspects the complete final diff and repository status; confirms code, tests, GDD, UI specs, and this file describe the same behavior; runs the final required validation; and returns one consolidated result. The report names changed files, delivered behavior, tests run and outcomes, unresolved risks, and any decision still required. Subagent completion messages are evidence, not a substitute for the Project Manager's final verification.

### Handoff contract

Every agent response must be concise, evidence-based, and use the following fields:

- `Scope`: what was and was not handled.
- `Evidence`: files, symbols, spec sections, commands, or reproduction observations.
- `Result`: decisions, edits, test outcomes, or severity-ranked findings.
- `Risks/Blockers`: unresolved items; write `None` when empty.
- `Next owner`: the exact role that should act next.

Role-specific payloads are mandatory: `game_designer` returns rules, values, invariants, edge cases, and acceptance criteria; `explorer` returns the execution path and affected-file map without edits; `gameplay_programmer` returns changed files and exact check results; `qa` returns criterion-by-criterion reproductions and results; `code_reviewer` returns severity-ranked findings or explicit approval. The Project Manager waits for all agents required by the current gate and consolidates their results instead of forwarding raw subagent output to the user.

## Key rules easy to get wrong (read before implementing)

- **Two-layer settlement (GDD §7.1):** individual word scores commit immediately; the sentence bonus is a *projection* overwritten every phase and only finalized at blind end. Never accumulate sentence bonuses per phase.
- **Owned Emoji Tile scoring order (changed 2026-09-03):** in the global owned-list `wordScoring` stage, each non-disabled physical owner resolves its Gray/Violet/Rainbow scoring edition before its own intrinsic effect and growth/decay beats, then advances left-to-right. Base/White add no scoring-edition beat. Tile-bound Emoji effects remain in the earlier played-tile phase, so Rare Earth and peers do not move; held-tile scoring remains after the complete owned list.
- **Conditional growth/decay presentation (changed 2026-09-04):** every conditional growth or decay trigger is presented immediately after its exact committed cause, before unrelated beats. For Glass, each actual destroyed material/result beat is followed by applicable growth beats in physical shelf order. Presentation never advances mechanics: Term Insurance and Type Foundry keep the pre-destruction value for the shattering word and apply growth from later words. Survival, Glass Insurance prevention, duplicate destruction attempts, and debuffs emit no destruction-growth beat. Preserve per-tile atomic order, instance/Echo attribution, event count, RNG, state, save shape, and `settleDurationMs()`; add no hook or timer merely to reposition an existing event.
- **Pattern matching (GDD §5.1):** whole-sequence match only; highest single pattern; articles/adjectives/adverbs are absorbed as modifiers (they don't break the skeleton, they add bonus). A gibberish hole voids all matches.
- **Run-scoped hidden sentence patterns (GDD §5.2, 2026-08-30; visual reference simplified 2026-09-04):** Run Info omits Object Complement, Ditransitive, and Complex entirely until the first successful actual submission whose existing post-boss `judgeSentence(sentenceSequenceForBlind(...))` result names that id as the highest pattern; Compound and the other eight remain public. Preview, failure, debuffed/removed words, and lower-ranked candidates never reveal. Preserve discoveries through the run/save/Continue, reset them on a new run, and never infer them from profile lifetime, Constellation levels, or finalized `patternPlayCounts`. Every visible pattern tooltip keeps its description and shows the §5.2 official example as uppercase word boxes only—no example heading, divider, role/POS labels, clause captions, arrows, or row breaks. Fill and border ordinary boxes with their selected POS tag colour; use a neutral marker tone for special grammar tokens such as ISNT rather than inventing a POS colour. List every example, including Compound and Complex, in one uninterrupted left-to-right row and horizontally scroll it only when the viewport is too narrow. Construct that UI-only content only after the discovery filter so hidden examples never enter the DOM or accessibility tree.
- **Run Info pattern-example spacing (changed 2026-09-04):** the one-row visual fills the tooltip width, centres the word-box group, and distributes boxes evenly; constrained viewports scroll horizontally without wrapping.
- **Rotating developer Laboratory (changed 2026-09-04):** the DEV-only Main Menu Laboratory is the single review surface for the latest completed player-facing implementation or change that cannot be inspected immediately in Collection or Run Info. This includes gameplay, audio, and animation work when those player-facing results meet that visibility criterion; internal-only refactors do not qualify. A new qualifying change replaces the prior contents; previews never accumulate, and automatic tests retain retired preview regressions. Reuse the real product component/data instead of copying it, and never add engine, RNG, run, discovery, profile, settings, or storage state for a preview. Preserve the shared 1440×988 shell, Back/Escape, EN/KO, accessibility, responsive layout, and Forced Colors. The current surface reuses production `ScoreTransferReadout` with deterministic UI-only `67 → 82` state, showing the remainder fall from `15 → 0` as the round total rises, without engine, RNG, run, or storage state. The former coffee-cup, money-ledger, money-total-motion, hidden-pattern, and Score Feedback previews remain covered by automated regressions.
- **Gibberish (GDD §6.4):** always submittable; pays letter chips × 1.0; no suit multiplier; layer-1 joker hooks fire on it, layer-2/3 naturally don't (suit/POS are null).
- **No global minimum word length (GDD §6.5).** The old fixed floor stays retired. Stereotype Plate is the sole conditional boss exception: it blocks any hand shorter than the longest valid word already played this Chapter (GDD §8.3–§8.4).
- **Bag never refills mid-blind (GDD §6.6)** — this is the intended natural cap on any long-blind or future phase-extension build. Zombie is the sole explicit exception: after a play, it returns every played physical letter tile to the current blind's undrawn bag.

Resolution is still gated on the settle-complete SIGNAL, never on the raw score (see the invariant below). The verdict beat is a fixed pace AFTER the signal, never a guess at settle length.

"Settlement sequence complete" is the single event that gates them (this unifies 04 A-1 and A-2). Concretely: `SettleProvider` (`src/ui/settle.tsx`) fires `onComplete` when its timeline lands → `useGame.markSettleComplete()` → `state.settleComplete` gates both the verdict overlay and `finalize`, then a short beat. **Never re-introduce a fixed delay to "wait for the settle"** — settle length is variable (it scales with the number of score beats and with game speed), so any constant undershoots long words and fires the verdict early. Explicit-slot reads/writes must be used by profile management so preview, deletion, or Reveal All never changes or contaminates another profile. On desktop the main process writes them to `%APPDATA%/Play the World/saves/{run,profile}.json`, which Steam Cloud syncs. The profile file additionally owns one main-process-only root `steamOwner`; it is outside `SAVE_KEYS`, profile slots, renderer snapshots, and generic write/remove IPC, and ordinary rewrites must preserve it. The active slot (`wj.profile`) and everything else (`wj.settings`, `wj.lang`, `wj.sortMode`) are machine-local preferences and stay in `localStorage` everywhere. A missing or invalid `wj.lang` may use only a sanitized `en|ko` hint from a successfully initialized packaged Windows Steam session for the first render; detection is never persisted, and raw Steam locale plus Steam id remain main-process-only. **Adding a persisted key means deciding which side it belongs on** — and `desktop/save-store.js` keeps a duplicate of `SAVE_KEYS` because `desktop/` cannot import from `src/`, so update both (a test fails if they drift). `run.json` and `profile.json` are separate on purpose: `persist.ts` DISCARDS a run whose `VERSION` moved, and one shared file would take the collection and lifetime stats with it. Reads must stay synchronous — the desktop backend loads once at boot through the preload bridge and serves reads from memory. `desktop/preload.cjs` must stay `.cjs`: a sandboxed preload has to be CommonJS even though the rest of the shell is ESM.

## Spec-conflict protocol (always apply)

The docs (`CLAUDE.md` + `docs/`) are the source of truth. When an instruction from the user conflicts with them — or two docs conflict with each other, or a request isn't covered at all — do NOT silently pick one. Instead:

1. **Stop and surface it.** Name the specific conflict: quote the doc rule (with its file + section) and the instruction that contradicts it. Don't bury it in a long reply — lead with it.
2. **Ask for the decision.** Offer the trade-offs briefly and ask which way to go. If the user's instruction is clearly the newer intent (they're explicitly changing direction), confirm that reading rather than assuming.
3. **Update the docs in the SAME change.** Once the user decides, edit the affected doc(s) so they match the decision — GDD/UI_DESIGN/screens-spec for design, this file for rules/architecture. Fix every stale cross-reference in the same pass (see principle 6). The decision is not "done" until the docs reflect it; code and docs land together.
4. **Record why, briefly.** For non-obvious reversals, leave a one-line note (a changelog bullet or an inline "(changed: …)" ) so the reasoning survives.

Never implement against a doc rule without doing this. A silent divergence between code and docs is the failure mode to avoid — the docs must always describe what the code actually does.

## Build order (vertical slices — implement in this order)

1. **Slice ① Core loop:** `rng.ts`, `bag.ts` (build from `BALANCE.bagComposition`, shuffle, draw), `lexicon.ts` (word `Set` from `data/dictionary.txt` + `data/lexicon.json` lookup), hand/discard state machine, word submission with letter-chip scoring + gibberish path. 3. **Slice ③ Sentences:** `patterns.ts` — POS assignment search, whole-sequence matchers for the 12 patterns, modifier absorption, highest-only, mutually exclusive Unison/register-synergy check; sentence finalization at blind end. This slice makes the game *fun* — test heavily (RUN×4 → chant; PIZZA TASTES GOOD → descriptive; hole voids pattern and register bonuses).
4. **Slice ④ Joker bus + first 6 jokers:** implement `JokerBus` wiring in the pipeline, then jokers #1, #2, #10 (layer 1), #12 (layer 2), #22, #24 (layer 3) as the proof set spanning all hook types.
5. **Slice ⑤ Blind/ante/shop:** blind state machine (small/big/boss), target curve, gold flows (clear reward / remaining phases / interest / sell), shop stock + reroll, then bosses and consumables.

## Data files (`data/`)

- `dictionary.txt` — lowercase ENABLE words up to 18 letters plus documented tile-grammar exceptions, the four curated MVP/VIP surfaces, and exact reviewed omissions from `lexicon-pipeline/curated-validity.json` (GDD §3.2), including apostrophe-free `aint` as Slang AIN'T with the auxiliary/linking-verb POS convention. This registry admits only listed spellings; it never opens a proper-name category or generates derivatives.
- `lexicon.json` — complete baked `{ word: { suit, pos[] } }` table. Register classification follows `docs/# 영단어 레지스터 분류 기준.md`; every entry has non-empty POS. Curated acronym metadata stays in `lexicon-pipeline/curated-abbreviations.json`, reviewed validity omissions stay in `curated-validity.json`, and both baked outputs consume both registries while runtime keeps its existing two-file loader.
