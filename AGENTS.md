# Play the Wor!d — Project Instructions

Balatro-inspired word-building roguelite for the web. **The full design document is `docs/GDD.md` — it is the single source of truth.** Every system referenced below cites its GDD section. Art direction is **pixel-art + CRT** (see `docs/UI_DESIGN.md`; the earlier ceramic/un-Balatro guardrail is retired).

## Architecture principles (non-negotiable)

1. **Headless engine.** All game logic lives in `src/engine/` and must never import DOM, React, or browser APIs. The engine must run in Node so `src/sim/` can autoplay thousands of runs for balance verification. UI (`src/ui/`) imports the engine, never the reverse.
2. **Jokers are data + hooks.** Every implemented joker (GDD §11) is a `JokerDef` object registering handlers on the event bus in `src/engine/events.ts`. Never hard-code a joker's effect inside pipeline code. If the pipeline lacks an event a joker needs, add the event. The active roster is Common 27 / Uncommon 44 / Rare 44 / Legendary 5 (120 total); Synesthete is retired, and the separate 97-tile redesign remains postponed.
3. **No magic numbers.** Every tunable value lives in `src/engine/balance.ts`, keyed to GDD tables. New numbers go there first.
4. **Seeded RNG.** All randomness (bag shuffle, shop stock, packs, boss draw) flows through one seeded RNG (`src/engine/rng.ts`, to be written — use a small PRNG like mulberry32/xoshiro). A run is fully reproducible from `RunState.seed`. Never call `Math.random()` in the engine.
5. **TypeScript strict mode.** The types in `src/engine/types.ts` encode GDD decisions (e.g. gibberish = `suit: null, posUsed: null`); keep them authoritative.
6. **Keep docs internally consistent.** When a patch changes a number or a mechanic, grep the docs for stale cross-references and update them in the same pass (e.g. changing the tile total means fixing every "N tiles" mention, not just §2.1; changing the settle/clear flow means updating the pipeline summary, not just the trigger section). Doc drift has caused real contradictions here more than once — a value or rule must read the same everywhere it appears.

## Key rules easy to get wrong (read before implementing)

- **Two-layer settlement (GDD §7.1):** individual word scores commit immediately; the sentence bonus is a *projection* overwritten every phase and only finalized at blind end. Never accumulate sentence bonuses per phase.
- **Pattern matching (GDD §5.1):** whole-sequence match only; highest single pattern; articles/adjectives/adverbs are absorbed as modifiers (they don't break the skeleton, they add bonus). A gibberish hole voids all matches.
- **Gibberish (GDD §6.4):** always submittable; pays letter chips × 1.0; no suit multiplier; layer-1 joker hooks fire on it, layer-2/3 naturally don't (suit/POS are null).
- **No minimum word length (GDD §6.5).** No current boss re-imposes one (the old "Editor" min-length boss was dropped in the 2026-07-21 roster; GDD §8.3–§8.4).
- **Bag never refills mid-blind (GDD §6.6)** — this is the intended natural cap on any long-blind or future phase-extension build.
- **Discard budget is per blind, not per phase (GDD §6.3).** Discarded tiles *exit play for the rest of the blind* (Balatro-aligned) — they do not return to the bag mid-blind; they come back only at blind end. Drawing replacements needs no RNG (they come from the remaining shuffled bag); the discard call still takes the seeded RNG for `discardGain` font-seal rolls (GDD §2.3).
- **Letter hands (GDD §5.5):** per-word structure bonuses fold into `WordScoringContext` before the suit multiplier settles; highest single hand only. **Vowel Flush and Straight fire on gibberish too** (jackpot); Twin/Triplet/Longword/Palindrome are valid-words-only.
- **Word length adds to Mult, it does not multiply (GDD §3.1, 2026-07-30):** `chips × (suitMult + length × BALANCE.wordLength.multPerLetter)`. **Valid words only** — gibberish stays `chips × 1.0` (§6.4), which also covers letterless Stone tiles (a word holding one always fails lookup). One helper, `wordLengthMult(letterCount, isGibberish)` in `src/engine/scoring.ts`, is the single source of truth: `scoreWord`, `loop.ts`'s `scoreSubmission`, and `engine/hint.ts` all call it. Forgetting `hint.ts` makes the Magnifier recommend the wrong word.
- **Auto-settle (GDD §7.2):** the blind auto-*detects* the clear (`pendingEnd` is set once projected ≥ target) and plays the full settle + sentence-finalize sequence — the bonus must be seen pushing the score over. There is **no intermediate "Cleared! + Settle button" verdict screen** (removed, item 4): after the finalized score lands (Stage 1) the round number rolls up, and after a short verdict beat the blind auto-resolves to the **Fee Settlement** modal (its own Collect button confirms) or, on a loss, to Game Over — `useGame`'s two-stage effect. The `earlyEndDisabled` flag still disables the early clear (settles only when phases run out) — a dormant hook no boss in the current roster sets (GDD §8.3, 2026-07-21; the old "Perfectionist" is retired). Resolution is still gated on the settle-complete SIGNAL, never on the raw score (see the invariant below). The verdict beat is a fixed pace AFTER the signal, never a guess at settle length.
- **The clear UI is gated on the settle-complete SIGNAL, never on the score (playtest-05 A — twice-recurring bug, treat as a first-class invariant):** the round-clear verdict *and* the Game Over UI may only appear after the settlement-sequence completion signal fires — never off the final score value, which the engine knows instantly. "Settlement sequence complete" is the single event that gates them (this unifies 04 A-1 and A-2). Concretely: `SettleProvider` (`src/ui/settle.tsx`) fires `onComplete` when its timeline lands → `useGame.markSettleComplete()` → `state.settleComplete` gates both the verdict overlay and `finalize`, then a short beat. **Never re-introduce a fixed delay to "wait for the settle"** — settle length is variable (it scales with the number of score beats and with game speed), so any constant undershoots long words and fires the verdict early. That exact mistake caused both recurrences; `settleDurationMs()` is the one source of truth for the timing.
- **Voucher slot (GDD §9.2):** immune to reroll; one purchase per chapter (`voucherLocked`); the offer is fixed per chapter (`run.voucherOffer`), restocked only when the Deadline/boss clears. Purchased vouchers never reappear; unpurchased ones may.
- **Blind skip + Editorial Perks (GDD §8.2, changed 2026-07-31):** Draft and Revision may be skipped; Deadline never may. Each Chapter's two seeded, uniformly rolled offers are fixed in `RunState.skipOffers` and fully disclosed on Blind Select. Skipping grants the current offer and advances directly with no scoring, Fee Settlement, clear/interest/remaining-resource payout, or Stationery Shop. Only effect text that explicitly permits copying may add another exception; never bypass the shared gate ad hoc.
- **The desktop build has no network and loads over `file://` (desktop packaging, 2026-07-29):** the game ships as an Electron app (`desktop/`, Windows, Steam-bound) that loads `dist/index.html` directly. Three kinds of change work perfectly in a browser and break **only** on desktop, so they are invisible during development: (a) a new CDN dependency — a font, script, or remote image; (b) loading data with a runtime `fetch()` — the dictionary and lexicon are bundled at build time via `?raw`/JSON imports in `src/ui/lexicon.browser.ts` and must stay that way; (c) making Vite's `base` absolute again — it is `'./'` and must stay relative so the same build runs from `file://`, the gh-pages `/D1/` subpath, and itch.io. `scripts/check-offline.mjs` (run by `build:desktop`) catches (a) and (c) automatically; (b) is on you. **The Electron app name `Play the World` (`app.setName` in `desktop/main.js`) must never change** — all player data lives under `%APPDATA%/<appName>/` (the save files and localStorage both), so renaming it orphans every player's save. `desktop/` imports no game code; the dependency direction is one-way (`desktop/ → dist/`). Packaged output goes to `../D1-release/` (outside the repo — packaging into the working tree fails with `EPERM` on this machine; see `docs/superpowers/specs/2026-07-29-desktop-packaging-design.md`).
- **Player progress goes through `src/ui/storage.ts` — never `localStorage` directly (file-based saves, 2026-07-29; three slots 2026-07-31):** the UI has exactly one persistence path. `SAVE_KEYS` in that file lists the eight progress keys (`wj.run`, `wj.collection`, `wj.collectionSeen`, `wj.lifetime`, `wj.unlocks`, `wj.vouchers`, `wj.tutorial`, `wj.tutorialIntro`); `storage.ts` multiplexes those values through three profile slots, with legacy flat values treated as P1. Profile creation/name and Reveal-All warning/applied/Challenge-disabled markers live inside each slot's `wj.lifetime`: P1 exists as `P1` by default, while P2/P3 are empty until created and blank creation names fall back to their `P#`. Profile tabs and creation only preview the explicit slot; **only Load Profile may change `wj.profile`**. The active slot shows disabled Current Profile and Delete Profile buttons; only a non-active created slot can be deleted, after two presses (warning, then exact-slot deletion). Explicit-slot reads/writes must be used by profile management so preview, deletion, or Reveal All never changes or contaminates another profile. On desktop they are written to `%APPDATA%/Play the World/saves/{run,profile}.json` by the main process, and Steam Cloud will sync that folder. The active slot (`wj.profile`) and everything else (`wj.settings`, `wj.lang`, `wj.sortMode`) are machine-local preferences and stay in `localStorage` everywhere. **Adding a persisted key means deciding which side it belongs on** — and `desktop/save-store.js` keeps a duplicate of `SAVE_KEYS` because `desktop/` cannot import from `src/`, so update both (a test fails if they drift). `run.json` and `profile.json` are separate on purpose: `persist.ts` DISCARDS a run whose `VERSION` moved, and one shared file would take the collection and lifetime stats with it. Reads must stay synchronous — the desktop backend loads once at boot through the preload bridge and serves reads from memory. `desktop/preload.cjs` must stay `.cjs`: a sandboxed preload has to be CommonJS even though the rest of the shell is ESM.

## Spec-conflict protocol (always apply)

The docs (`CLAUDE.md` + `docs/`) are the source of truth. When an instruction from the user conflicts with them — or two docs conflict with each other, or a request isn't covered at all — do NOT silently pick one. Instead:

1. **Stop and surface it.** Name the specific conflict: quote the doc rule (with its file + section) and the instruction that contradicts it. Don't bury it in a long reply — lead with it.
2. **Ask for the decision.** Offer the trade-offs briefly and ask which way to go. If the user's instruction is clearly the newer intent (they're explicitly changing direction), confirm that reading rather than assuming.
3. **Update the docs in the SAME change.** Once the user decides, edit the affected doc(s) so they match the decision — GDD/UI_DESIGN/screens-spec for design, this file for rules/architecture. Fix every stale cross-reference in the same pass (see principle 6). The decision is not "done" until the docs reflect it; code and docs land together.
4. **Record why, briefly.** For non-obvious reversals, leave a one-line note (a changelog bullet or an inline "(changed: …)" ) so the reasoning survives.

Never implement against a doc rule without doing this. A silent divergence between code and docs is the failure mode to avoid — the docs must always describe what the code actually does.

## Build order (vertical slices — implement in this order)

1. **Slice ① Core loop:** `rng.ts`, `bag.ts` (build from `BALANCE.bagComposition`, shuffle, draw), `lexicon.ts` (word `Set` from `data/dictionary.txt` + `data/lexicon.json` lookup), hand/discard state machine, word submission with letter-chip scoring + gibberish path. Tests: bag counts, discard budget, gibberish scoring.
2. **Slice ② Suits + projection:** suit multiplier application, committed vs projected score split, early-end trigger (`projected >= target`).
3. **Slice ③ Sentences:** `patterns.ts` — POS assignment search, whole-sequence matchers for the 12 patterns, modifier absorption, highest-only, Unison check; sentence finalization at blind end. This slice makes the game *fun* — test heavily (RUN×4 → chant; PIZZA TASTES GOOD → descriptive; hole voids match).
4. **Slice ④ Joker bus + first 6 jokers:** implement `JokerBus` wiring in the pipeline, then jokers #1, #2, #10 (layer 1), #12 (layer 2), #22, #24 (layer 3) as the proof set spanning all hook types.
5. **Slice ⑤ Blind/ante/shop:** blind state machine (small/big/boss), target curve, gold flows (clear reward / remaining phases / interest / sell), shop stock + reroll, then bosses and consumables.

6. **Slice ⑥ UI (play screen):** follow `docs/UI_DESIGN.md` — tokens, layout, components, and juice priority order are specified there. **The visual contract is `docs/mockups/play-screen.html`; match it.** React + plain CSS custom properties (no Tailwind on game screens). The UI only reads engine state snapshots and replays the engine's per-submission score-event log for the settle animation; never put game rules in components. **Art direction: pixel-art + CRT** (Balatro lineage; the earlier "ceramic-tile, deliberately un-Balatro" identity and its trade-dress guardrail are RETIRED — see UI_DESIGN.md). Adopt the pixel-art idiom, CRT post-effect, and screen grammar freely; only avoid copying Balatro's *specific* art assets (its actual card illustrations, logo, exact sprites). Existing components are restyled (pixelation, squared corners, blocky shadows, global CRT pass), not rebuilt — semantic tokens and layout stay. Pixel-art shop mascot (tuxedo cat proprietor) per UI_DESIGN §6.

After each slice, write a tiny scenario in `src/sim/` exercising it headlessly.

## Data files (`data/`)

- `dictionary.txt` — complete lowercase ENABLE pool plus documented tile-grammar exceptions (GDD §3.2).
- `lexicon.json` — complete baked `{ word: { suit, pos[] } }` table. Register classification follows `docs/# 영단어 레지스터 분류 기준.md`; every entry has non-empty POS.
- The reproducible POS/register pipeline lives in `lexicon-pipeline/` and runs offline only. Never fetch or classify words in the game runtime.

## Stack

- TypeScript (strict), Vite, Vitest.
- UI: React for the prototype; engine/renderer separation means it can be swapped for PixiJS later if animation demands grow.
- No server; everything client-side. Persistence via localStorage can come later (not in slices ①–⑤).
