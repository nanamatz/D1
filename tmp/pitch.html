2. 구조 설명 — AI가 안전하게 일하도록 만든 아키텍처

2.1 헤드리스 엔진 / UI 완전 분리

src/engine/의 모든 게임 로직은 DOM·React·브라우저 API를 일절 import 하지 않는다. 의존 방향은 단방향이다 — UI → 엔진, 역방향 없음.

src/engine/   게임 규칙 (Node에서 단독 실행 가능, 브라우저 무관)
src/ui/       React 화면 — 엔진 상태 스냅샷을 읽어 그릴 뿐 규칙을 갖지 않음
src/sim/      자동 플레이 시뮬레이터 — 수천 런을 돌려 밸런스 검증

이 분리의 목적은 AI가 자기 작업을 검증할 수 있게 하는 것이다. 엔진이 브라우저에 묶여 있었다면 밸런스 변경의 결과는 사람이 손으로 플레이해야만 알 수 있다. 헤드리스이기 때문에 에이전트가 npm run sim:full-run 같은 명령으로 수천 판을 즉시 돌려 "이 수치를 바꾸면 클리어율이 얼마나 변하는가"를 스스로 측정한다.

2.2 규칙은 코드가 아니라 데이터

AI가 가장 쉽게 망가뜨리는 것이 특수 케이스 하드코딩이다. 그래서 규칙 계열 전부를 데이터 + 이벤트 훅으로 못 박았다.

계열형태강제 규약
이모지 타일 120종JokerDef 객체가 이벤트 버스에 훅 등록파이프라인 코드에 개별 효과를 절대 쓰지 않는다. 필요한 이벤트가 없으면 이벤트를 추가한다
보스 16종BossDef위와 동일
노름꾼 카드 14종GamblerDef + 단일 진입점 useGambler()카드마다 별도 경로를 만들지 않는다
편집 특전 26종skipRewards.ts 단일 풀컴포넌트가 효과를 재구현하지 않는다
모든 수치src/engine/balance.ts 한 곳매직 넘버 금지. 새 수치는 여기 먼저 들어간다
난수src/engine/rng.ts 시드 RNGMath.random() 호출 금지 — 런은 시드만으로 완전 재현된다

덕분에 "새 이모지 타일 추가"는 파일 하나 추가 + 인덱스 한 줄이 되고, 에이전트가 기존 파이프라인을 건드릴 이유 자체가 사라진다.

2.3 CLAUDE.md — 에이전트 규약 문서

저장소 루트의 CLAUDE.md는 AI가 매 세션 시작 시 반드시 읽는 상시 지시서다. 사람이 읽는 README와 별개로, 에이전트의 기본 습관을 덮어쓰기 위해 존재한다. 크게 네 부분이다.

1. 아키텍처 불변 원칙 (위 2.1~2.2)
2. 틀리기 쉬운 규칙 목록 — 과거에 실제로 AI가 틀렸던 지점을 사후에 문서화한 것
3. 스펙 충돌 프로토콜 — 지시와 문서가 충돌하면 조용히 고르지 말고 멈추고 물어라
4. 문서 동기화 의무 — 수치를 바꾸면 그 수치를 언급한 모든 문서를 같은 커밋에서 고친다

2.4 자동 검증 게이트

빌드 한 번에 다음이 전부 돌고, 하나라도 실패하면 빌드가 죽는다. AI 산출물의 안전망이다.

검사잡는 것

check-locales한국어/영어 번역 키 누락·불일치
check-assets카드·바우처 이미지 규격 및 누락

특히 check-offline은 AI가 무심코 CDN 폰트나 원격 스크립트를 추가하는 사고를 자동으로 막는다. 브라우저에서는 멀쩡히 돌고 오프라인 데스크톱 빌드에서만 깨지는, 개발 중에는 보이지 않는 종류의 결함이다.

3. AI 대상 주요 프롬프트 및 지시 사항

3.1 상시 지시서에서 실제로 쓰인 문장 (발췌)

> 헤드리스 엔진. 모든 게임 로직은 src/engine/에 있고 DOM, React, 브라우저 API를 절대 import 하지 않는다. 엔진은 Node에서 실행되어야 하며, src/sim/이 수천 런을 자동 플레이해 밸런스를 검증할 수 있어야 한다. UI는 엔진을 import 하고, 그 역은 없다.

> 이모지 타일은 데이터 + 훅이다. 모든 타일은 이벤트 버스에 핸들러를 등록하는 JokerDef 객체다. 타일의 효과를 파이프라인 코드 안에 하드코딩하지 마라. 파이프라인에 필요한 이벤트가 없다면 이벤트를 추가하라.

> 매직 넘버 금지. 모든 조정 가능한 값은 src/engine/balance.ts에 GDD 표와 대응되는 키로 존재한다. 새 수치는 거기 먼저 들어간다.

> 시드 RNG. 모든 무작위성은 src/engine/rng.ts의 시드 RNG를 통과한다. 런은 RunState.seed만으로 완전히 재현된다. 엔진에서 Math.random()을 절대 호출하지 마라.

> 문서 일관성 유지. 패치가 수치나 메커니즘을 바꾸면, 문서 전체에서 낡은 상호 참조를 찾아 같은 작업에서 함께 고쳐라. 문서 드리프트는 이 프로젝트에서 실제로 여러 번 모순을 만들었다 — 하나의 값이나 규칙은 등장하는 모든 곳에서 동일하게 읽혀야 한다.

> 스펙 충돌 프로토콜. 사용자의 지시가 문서와 충돌하거나, 문서끼리 충돌하거나, 아예 다뤄지지 않은 요청이면 조용히 하나를 고르지 마라. (1) 충돌을 먼저 드러내고 — 문서 규칙을 파일·절과 함께 인용하고 (2) 결정을 요청하고 (3) 결정되면 같은 변경에서 문서를 함께 고치고 (4) 비직관적인 번복이면 이유를 한 줄 남겨라.

3.2 반복 사용한 작업 지시 패턴

작업 하나를 던질 때 항상 같은 순서를 강제했다.

1) 브레인스토밍  — 무엇을 만들 것인지 합의. 코드 금지.
2) 스펙 작성     — docs/superpowers/specs/<날짜>-<기능>-design.md
3) 계획 작성     — docs/superpowers/plans/<날짜>-<기능>.md (단계별, 검증 지점 포함)
4) 구현          — 계획대로. 단계마다 테스트 실행.
5) 검증          — 주장하기 전에 명령을 실제로 돌리고 출력으로 증명.

docs/superpowers/에는 이렇게 생성된 스펙·계획 문서 30여 편이 그대로 남아 있고, 각 기능이 어떤 근거로 지금 모습이 되었는지 추적된다.

또한 플레이테스트 피드백은 증상이 아니라 규칙으로 환원해서 지시했다. 예:

> "정산이 끝나기 전에 클리어 화면이 뜬다"를 고칠 때, 고정 지연(setTimeout)을 절대 넣지 마라. 정산 길이는 단어 길이와 게임 속도에 따라 변하므로 어떤 상수든 긴 단어에서 어긋난다. 클리어 판정 UI는 오직 정산 완료 신호에만 걸려야 한다.

이 한 줄이 규약 문서에 들어간 뒤 같은 버그가 재발하지 않았다. 버그 수정 프롬프트의 결과물은 코드가 아니라 규칙이어야 한다는 것이 이 프로젝트에서 얻은 가장 큰 교훈이다.

3.3 이미지 생성 지시

이모지 타일 120종을 포함한 픽셀 아트는 생성형 이미지 AI로 만들되, 일관성을 프롬프트가 아니라 규격으로 잡았다.

  • 고정된 시각 문법을 지시서에 명문화: 짙은 남색 판, 흰/빨강/노랑/시안 3~5색, 큰 실루엣 하나, 하드 픽셀 엣지 — 초창기 아케이드 게임의 문법
  • 생성 결과는 스크립트로 정규화: normalize-pack-art.mjs, build-voucher-assets.mjs, trace-pixel-svg.mjs
  • check-card-assets.mjs가 규격 이탈·누락을 빌드에서 차단
  • 런타임 카드 규격(124×165px)에 맞지 않는 이미지는 잘리거나 왜곡되지 않고 object-fit: contain + 니어리스트 네이버로 확대

3.4 어휘 데이터 분류

172,251개 영단어 각각에 품사(POS) 와 레지스터 슈트(Formal / Standard / Slang / Vulgar)를 부여해야 했다. 사람이 손으로 할 수 있는 양이 아니고, AI에게 통째로 맡기면 일관성이 무너진다. 그래서 이렇게 했다.

1. 분류 기준 문서를 먼저 작성 — "대표 의미 기준", 즉 그 단어의 첫 번째 영어 정의가 붙은 라벨로 판정한다. informal/구어 및 무표지 의미는 Standard로 남긴다. 애매하면 전부 Standard로 기본 처리한다(오탐보다 미탐이 낫다).
2. Wiktionary 용법 카테고리로 후보만 좁힌다 (전수 판정이 아니라 후보 탐색).
3. 후보에 대해 기준 문서를 적용해 분류하고, 품사가 호환되는 굴절형만 라벨을 상속시킨다.
4. 결과 분포와 근거 경로를 register-audit.json에 전량 기록해 사후 검증 가능하게 남긴다.

최종 분포: Standard 168,463 / Formal 2,669 / Slang 879 / Vulgar 240. 이 비대칭 자체가 게임의 리스크-리워드 곡선이 된다 — Vulgar 배수가 ×3.0인 이유는 만들기 어렵기 때문이고, 그 난이도는 기획 수치가 아니라 실제 데이터 분포다.

모든 결과물은 빌드 시점에 정적 파일로 구워져 번들에 포함된다. 런타임에는 AI도 네트워크도 전혀 개입하지 않는다 — 게임은 완전한 오프라인 클라이언트다.

5. 재현성 — 검증 가능한 형태로 남긴 것

  • 런 전체가 시드 하나로 재현된다. 모든 무작위(주머니 셔플, 상점 재고, 팩, 보스 추첨)가 단일 시드 RNG를 통과한다.
  • 밸런스 주장은 시뮬레이션으로 증명한다. src/sim/의 자동 플레이 스크립트가 수천 런을 돌려 클리어율·점수 분포를 출력한다.
  • 모든 설계 결정이 문서로 남는다. docs/GDD.md(단일 진실 소스), docs/UI_DESIGN.md, docs/screens-spec.md, docs/superpowers/의 스펙·계획 30여 편.
  • 엔진 규칙은 테스트로 고정된다. 슬라이스별 테스트가 tests/에 있고, 빌드마다 실행된다.
